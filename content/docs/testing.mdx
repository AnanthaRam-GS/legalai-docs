LegalAI is tested at four levels: fast unit and contract tests, database-backed integration tests on an isolated database, end-to-end browser journeys, and supervised live runs against real models. Continuous integration runs the first three on every pull request. Data changes have their own safeguards.

## Test suites at a glance

| Suite               | Runner                     | Size on `main` (25 October 2026)                           |
| ------------------- | -------------------------- | ---------------------------------------------------------- |
| Backend tests       | Python `unittest`          | 951 test methods in 81 modules, 12 of them database-backed |
| Frontend tests      | Vitest and Testing Library | 291 test cases in 40 files                                 |
| End-to-end journeys | Playwright (Chromium)      | 15 tests in 6 spec files                                   |

These are counts of tests defined in the code at commit `ed3cc76`, not a record of a passing run. Database-backed modules run separately from the rest so that nothing touches development data.

## Continuous integration

GitHub Actions runs four jobs on every pull request and every push to `main`. No job uses a secret, calls an LLM provider, downloads a model or reads the real corpus.

| Job            | What it runs                                                                           |
| -------------- | -------------------------------------------------------------------------------------- |
| `backend-unit` | The non-database suites, with Tesseract installed; fails if the OCR tests were skipped |
| `backend-db`   | The 12 database-backed modules against a throwaway PostgreSQL service                  |
| `frontend`     | ESLint, Prettier, the TypeScript check, Vitest and a production build                  |
| `e2e`          | The Playwright journeys against the real backend and frontend in fake mode             |

Five tests need the real corpus or model cache, which a clean checkout does not have; they are skipped in CI with a stated reason and run locally.

## End-to-end journeys

The journeys cover public questions (text, out of scope and an FIR upload), registration with an email code, the lawyer workspace (precedents, an FIR brief, history and the five analytics tabs), admin store health with an ingestion and a duplicate upload, access control, and a 375 px layout.

In CI they run in a **test-only fake mode**: a deterministic answer model that cites the retrieved evidence, a hashing embedder and an overlap reranker over six invented judgments. The backend refuses this mode outside the test environment. A local real mode runs the same journeys with the real retrieval models against a restored copy of the development data. The screenshots on this site come from the real application, never from fake mode.

## Isolated test database

Database-backed modules import a bootstrap before anything else. It:

1. Requires `TEST_DATABASE_URL` and aborts unless the database name ends in `_test` and differs from the development database.
2. Migrates the test database to the latest schema.
3. Redirects Chroma, BM25, uploads and verification proofs to a temporary directory that is deleted on exit.
4. Blanks every external credential, forces console email, and blocks network and SMTP connections.
5. Blocks loading the real embedding and reranking models unless explicitly allowed, and keeps Hugging Face offline.

Every test starts from truncated tables. This setup exists because earlier test runs had written fixtures into the development database; the [reconciliation](/results/#reconciliation) cleaned that up.

## Contract tests

- **Error contract:** a test calls every registered route in every way it can fail and checks that each error has the `{error, code, detail}` shape.
- **Negative authorization:** a database suite checks that each role is refused the routes it may not use.
- **Model devices:** rankings on all 30 benchmark queries must be identical on CPU and Apple MPS; a slow mocked PDF query must not block `/health`.
- **OCR:** fixture scans must reach at least 95% character accuracy; tests skip with a reason when Tesseract is missing.
- **NCRB extraction:** the extractor's output must be byte-for-byte reproducible from the recorded PDF.

## Before and after any data change

1. **Snapshot** row counts (read-only) and file hashes of every store.
2. **Back up** the database and both indexes, with a checksum manifest, outside the repository.
3. **Verify the backup** by restoring it into a separate rehearsal database and comparing counts.
4. **Rehearse** the change on the rehearsal database and store copies: dry run, run, second run (which must make 0 changes).
5. **Run on development** the same way, then confirm the analytics verifier reports `RECONCILED` and the store verifier reports `CONSISTENT`.

## Supervised live runs

Live runs send real questions through the full pipeline with a live answer model, record identifiers, timings and pass/fail checks in the repository, and keep full responses outside it for legal review. Each run checks that sources are validated citations only, that excerpts and evidence references resolve to real chunks, and that no stack trace reaches the user.
